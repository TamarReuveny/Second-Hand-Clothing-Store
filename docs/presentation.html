ReWear

Give your closet a second life

Second-hand clothing marketplace, built and shipped by
Tamar Reuveny & Neta Yaar

The problem

Good clothes sit unused. Buyers who want them have no easy way in.

People have used clothing that still has real value — and other people want affordable, sustainable clothing but don't have a simple, trustworthy way to buy it from individual sellers online.

What sellers have

Closets full of clothes they've outgrown, or never wear — sitting idle instead of earning anything.

What buyers want

Good style at a lower price and a lower footprint — without digging through unreliable listings.

Who it's for

A two-sided marketplace, buyer-first

Buyers

The primary user and the paying customer. The whole experience is optimized around browsing, filtering, and buying with confidence.

Sellers

Anyone can list — a marketplace needs supply. Get a real channel to sell, manage listings, and build a rated reputation.

Admin (planned)

Moderates listings and reports, keeps the catalog trustworthy. Scoped for a future version.

Why it matters

Four business goals drove every feature decision

  • —Reduce waste, save money. Every completed sale keeps a garment in use and out of landfill.
  • —Buy with confidence. Search, filters, real photos, and seller ratings replace guesswork.
  • —Low friction to list. A seller can go from "I have this jacket" to "it's live" in under a minute.
  • —Build trust between strangers. Star ratings tied to real completed orders, not self-reported claims.

How it's built

No hand-written API — Server Actions are the API

Browser
Client Components
Forms, filters, favorite / cart buttons — the interactive slice only
↓ HTTPS
Next.js 16
Server Components + Server Actions
Pages read data directly; every write is a typed server function, not a REST endpoint
↓ anon key, RLS-scoped
Supabase
Postgres + Auth + Storage
Row Level Security enforces every read and write — the real security boundary

Middleware

proxy.ts refreshes the Supabase session cookie on every request, so server-rendered pages always see current auth state.

Type safety

TypeScript end to end — DB types hand-modeled to match the schema, route types auto-generated by Next.js.

Styling

Tailwind CSS v4, a custom cream/forest palette and serif type — no template UI kit.

Deployment

Two connected platforms, one push each

GitHub
Source of truth
Every change is a commit on main — the whole history of the build is in the repo
↓ push triggers a build
Vercel
Hosts the Next.js app
Auto-deploys on every push to main; env vars (Supabase URL/key) set once in project settings
↓ connects at runtime
Supabase
Hosts the database
Schema changes are numbered SQL migration files, run by hand in order — no ORM migration tool

A real deploy failure, fixed

One push failed to build on Vercel: the lockfile had 65 packages resolving to a private company registry instead of the public npm one — unreachable from Vercel's build servers. Regenerated the lockfile against the public registry and it deployed clean. Free-tier Supabase also auto-pauses after a week idle — a one-click "Resume" in the dashboard, something we hit and solved more than once.

Notable

Orders are never inserted directly — a single Postgres function atomically checks availability, locks the row, marks the listing sold, and records the order. Two buyers can't both "win" the same item.

What actually happened

The e2e buy-flow test found that a buyer got a 404 viewing their own just-purchased item. Root cause: a column-name collision inside a database security policy — orders has its own id column, so an unqualified reference silently pointed at the wrong table. Tests against the real database caught what a mocked unit test never would have.

Security

Row Level Security is the boundary — not app code

  • —Authentication via Supabase Auth; no custom password handling.
  • —Authorization enforced in Postgres — a bug in a page's if check is a bug, not a data breach.
  • —Server Actions are same-origin only by default (CSRF) with an 8MB body cap.
  • —Secrets: only the public anon key is ever used — confirmed by grep, not just habit.

Known, and documented

Checkout is simulated — card data is format-validated but never transmitted or stored. Photo type-checking trusts the browser's MIME claim. No rate limiting yet. All written up, not swept under the rug.

Scale

Fine at tens of users. Here's what breaks first.

  • —No pagination anywhere — the biggest concrete gap. Every list query fetches everything.
  • —The seller-rating filter aggregates every review row in app code on each request.
  • —A few missing indexes on actively filtered/sorted columns as data grows.
  • —Item page fires 7 queries sequentially instead of in parallel.

If we had more time

The next five things we'd build

  1. Pagination across the browse grid, listings, orders, and favorites.
  2. Real payments via a processor like Stripe, replacing the simulated checkout.
  3. Rate limiting on signup, login, and listing creation.
  4. Image optimization pipeline for uploaded photos.
  5. Admin moderation & notifications — both already scoped in the original product spec.
